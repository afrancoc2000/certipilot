Confusion lock: CA = rule-based (you write group/location /device conditions) → P1. Identity Protection = risk-based (ML scores user & sign-in) → P2. PIM = elevated roles → P2. MFA enforcement = CA Grant control. Grant = require/block (MFA, hybrid join, compliant device, Terms of Use). Session = sign-in frequency, persistent browser, app-enforced restrictions, CAE. Risk policies only when the requirement says "risky".

🌳 Hybrid identity: auth method + sync engine

① Auth method — how users sign in
Default, simplest, leaked-credential detection →PHS
Password hash must stay on-prem (≥2 agents for HA) →PTA
AD FS-style: smart cards, on-prem MFA, custom claims →Federation
② Sync engine — which tool provisions
Lightweight, ≤150k objects, multi-forest / disconnected →Cloud Sync
Device sync (Hybrid Join), group writeback, Exchange hybrid →Connect Sync
PHS works with both engines. Cloud Sync = PHS only; PTA & Federation need Connect Sync. PHS is the default recommendation. Entra DS needs NTLM/Kerberos hashes → enable PHS even with PTA/Fed; cloud-only users reset password once after Entra DS.

🌳 Authorization (RBAC / ABAC / custom)

Built-in role fits exactly →Built-in role
Built-in too broad (Storage / Key Vault) →+ ABAC condition
Unique permission set, nothing fits →Custom role
Least privilege scope: Resource > Resource Group > Subscription > Management Group. Built-in always preferred over custom.

🌳 Security posture (Defender vs Sentinel)

Score / posture / recommendations across hybrid + multi-cloud →Defender for Cloud
SIEM/SOAR, collect logs, KQL hunt, playbook on alert →Sentinel
The verb decides: score → Defender; hunt/respond → Sentinel.
Not this trio: Purview = govern/classify the data itself (out of AZ-305 scope, DP/SC). Sentinel watches traffic · Defender scores posture · Purview inventories cargo.
