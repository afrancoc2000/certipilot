🌳 SQL family selection

OS access, SQL Agent cross-DB, FileStream, CLR, SSAS/SSRS on box, BYOK HSM →SQL on VM (IaaS)
Most SQL features (cross-DB, Agent, Broker, linked servers) + PaaS + VNet →SQL MI
Single-DB / SaaS multi-tenant, max PaaS abstraction →SQL Database
SQL MI = delegated subnet /27. Enterprise / Always On AG lift-shift → Business Critical (built-in HA).

🌳 Cosmos DB API selection

SQL queries + relational tables + geo-replication→PostgreSQL
Document JSON, greenfield (flagship)→NoSQL / Core
Existing MongoDB app→MongoDB
Existing Cassandra app→Cassandra
Existing Gremlin graph app→Gremlin
Azure Table app + global + autoscale→Table
Cosmos is the storage answer for SLA on read/write latency + throughput + consistency + availability.

🌳 PostgreSQL: 1 node vs sharded

Fits on one node (vertical scale + read replicas)
OLTP · web/app backends · single / low-tenant SaaS→Flexible Server
Outgrew one node → shard writes/storage
Multi-tenant SaaS (shard by tenant_id) · real-time analytics · high-ingest time-series→Cosmos for PostgreSQL (Citus)
Not a Cosmos API pick — vanilla PostgreSQL. Citus only after vertical scale + read replicas run out.

🌳 Cosmos consistency level

Never stale, any latency cost OK→Strong
Bounded lag (time/versions), cheaper than Strong→Bounded Staleness
Read-your-own-writes per user (web) — DEFAULT→Session
Write-order reads, freshness unbounded→Consistent Prefix
No order, cheapest, lowest latency→Eventual
"Sober Bartenders Serve Cold Eggnog" · Multi-write → Session or weaker.

🌳 Storage account type

Storage ABAC: RBAC + condition on resource/request/principal attrs. Blobs/ADLS + Queues ✅; Files/Tables ❌.
